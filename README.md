# Лабораторная работа: потоки, процессы и асинхронность в Python

**Цель работы:** понять отличия между потоками и процессами и понять, что такое
асинхронность в Python.

Работа состоит из двух задач:
- **Задача 1** - посчитать сумму чисел тремя способами (`threading`, `multiprocessing`,
  `async`). Это тяжёлые вычисления (нагрузка на процессор, CPU).
- **Задача 2** - параллельно спарсить веб-страницы и сохранить заголовки в БД теми же
  тремя способами. Это ожидание сети (I/O).

## Описание программ

**Задача 1.** Диапазон чисел `1..N` делится на `WORKERS` равных кусков. Функция
`calculate_sum(start, end)` считает сумму своего куска. Три программы отличаются только
способом запуска кусков: потоки, процессы, корутины. Правильность проверяется формулой
Гаусса: `1 + 2 + ... + N = N * (N + 1) / 2`.

По заданию `N = 10 000 000 000 000`, но обойти такой цикл в Python - это около 90 часов,
поэтому в коде стоит `N = 100 000 000` (100 млн): время измеримое, а правильность всё
равно подтверждается формулой. Поменять можно в начале файлов.

**Задача 2.** Функция `parse_and_save(url)` скачивает страницу, достаёт заголовок
`<title>` через BeautifulSoup и сохраняет `url` и заголовок в SQLite. Список URL
(`task2_parsing/db.py`) обрабатывается тремя способами.

> **Про базу данных.** Используется SQLite - файл `lab1.db` создаётся автоматически рядом
> со скриптами, таблица `pages(id, url, title)`. Если в твоей лабораторной №1 база с другой
> схемой или названием - поменяй `DB` и SQL-запросы в `db.py` под свою таблицу.

## Особенности подходов

| Подход | Что это | Сильная сторона | Слабая сторона |
|---|---|---|---|
| `threading` | несколько потоков, но GIL пускает «к плите» одного за раз | хорош для ожидания (сеть, диск) | не ускоряет вычисления |
| `multiprocessing` | отдельные процессы на разных ядрах | реально ускоряет вычисления | дорогой запуск, тяжёлый обмен данными |
| `async` | один поток, переключение на `await` | тысячи ожидающих задач без лишних потоков | не ускоряет вычисления, нужен async-код |

## Комментарий к сравнению

Два эксперимента дают зеркальный результат, и в этом вся суть работы:

- В **Задаче 1** (вычисления) побеждает **multiprocessing** - он реально использует
  несколько ядер. `threading` и `async` идут вровень с обычным последовательным кодом,
  потому что мешает **GIL**: потоки и корутины делят одно ядро.
- В **Задаче 2** (сеть) всё наоборот: побеждают **async** и **threading**, потому что
  программа почти всё время ждёт ответа сервера, и это ожидание оба подхода тратят с
  пользой. `multiprocessing` тоже ускоряет, но запуск процессов «съедает» часть выигрыша.

**Как выбирать на практике:**
- тяжёлые вычисления (CPU) -> `multiprocessing`;
- много ожидания (сеть, файлы) -> `async` (когда запросов очень много) или `threading`
  (когда хочется проще).

## Аналогия простыми словами

Представь кухню:
- **поток** - несколько поваров на одной плите (готовит один за раз - это GIL);
- **процесс** - у каждого повара своя кухня со своей плитой (реально параллельно);
- **async** - один шустрый повар-жонглёр: пока блюдо в духовке, начинает следующее.

Поэтому для расчётов нужны отдельные плиты (процессы), а для ожидания достаточно не
простаивать (потоки/async).
